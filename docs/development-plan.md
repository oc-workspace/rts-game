# rts-game 开发计划

## 1. 计划定位

这是一份面向第一版可玩 vertical slice 的开发计划，不是一次性实现“绝对完美”的承诺。计划把愿景拆成连续的可验收阶段，每个阶段都要求能运行、能验证、能回退。

估算假设：一名主要开发者配合 AI 辅助，按每周约 4 至 5 个有效开发日推进。实际节奏以每个里程碑的验收结果为准；如果资产制作或性能问题超出预期，优先保护玩法闭环和可测试性。

## 2. 开发环境约定

实际开发从远程 dev 工作区开始：

~~~text
ssh rococo-oc-workplace
cd /work/oc-projects/rts-game
~~~

本地工作区只承担文件准备、文档编辑和同步辅助；远程目录才是开发仓库的实际工作树。每次 P1/P2 变更完成后，应在远程目录运行类型检查、构建或 smoke test，再使用 oc-push 推送 dev。生产仓库的同步必须走 rococo-root 隔离目录、oc-prod-release 和 PR。

## 3. 目标与非目标

### 第一版目标

- 在浏览器中运行一个 3D 太空 RTS 随机遭遇。
- 支持至少三类舰船和两方阵营。
- 支持选择、框选、移动、攻击、停止、暂停和重新开始。
- 支持基础编队、战斗结果和 HUD 信息反馈。
- 具备固定 seed、基础视觉效果、性能压力场景和可重复构建。

### 第一版非目标

- 不做战役、任务编辑器、联机、外交、完整经济系统或多人同步。
- 不先做大量舰船资产，再等待玩法落地。
- 不把 AI 子代理数量、循环次数或代码量当作完成标准。
- 不在没有性能数据的情况下承诺商业 AAA 级质量。

## 5. 分阶段开发内容

### P0：项目基线（已完成）

完成内容：

- 建立开发仓库和生产仓库同步链路；
- 明确 Three.js 核心路线；
- 记录项目背景、技术对比、发布流程和进度格式；
- 建立本技术方案与开发计划。

退出标准：

- 新开发者能够从文档找到仓库、启动、发布和下一步任务；
- dev 和 prod 的职责边界明确。

### P1：工程骨架

任务顺序：

1. 初始化 TypeScript、Vite 和 Three.js；
2. 添加开发启动、构建、类型检查和测试命令；
3. 建立 App Shell、配置和错误边界；
4. 创建 renderer、scene、camera、resize 和 animation loop；
5. 创建基础 UI root 与调试面板；
6. 加入固定 seed 配置和版本信息显示。

验收标准：

- 本地启动后能看到清晰的 3D 背景和调试信息；
- 浏览器调整尺寸不会错位或报错；
- 生产构建成功；
- renderer 创建失败时显示明确提示；
- 可通过一个固定 seed 启动同一场景。

### P2：单舰闭环

任务顺序：

1. 定义 Unit、ShipClass、Order 和 WorldState；
2. 建立固定步长 simulation；
3. 创建一艘可辨识的测试舰；
4. 实现相机平移、缩放、旋转和聚焦；
5. 实现单击拾取、选择框和选中高亮；
6. 实现右键移动、停止、暂停和重新开始；
7. 添加单位状态卡片。

验收标准：

- 玩家能从开始到重新开始完成一次完整控制闭环；
- Simulation 不依赖 Three.js Mesh 才能运行；
- 同一个 seed、同一组输入得到一致的移动结果；
- 选中反馈在不同镜头距离下仍可读。

### P3：战斗闭环

任务顺序：

1. 定义侦察、战斗、主力三类 ShipClass；
2. 加入双方阵营和基础颜色规则；
3. 实现目标选择、攻击范围、冷却和伤害；
4. 实现死亡、移除和战斗结果；
5. 加入攻击指令、停止指令和简单敌方行为；
6. 在 HUD 展示生命值、目标和冷却状态。

验收标准：

- 三类舰船在速度、生命值、射程或伤害上有可观察差异；
- 攻击命中、受伤和销毁状态可复现；
- 没有目标时不会产生无界错误或死循环；
- 一局最小战斗可以自然结束。

### P4：随机模式与 HUD

当前进度：P4.1 至 P4.3 已完成 deterministic random、随机舰队生成、编队出生点、中立小行星、战场边界、框选/多选、控制组、队列指令、舰队列表、seed 复制/重开/新局入口、战斗日志、遭遇状态面板和小地图相机导航。P4 的计划范围已经闭环。

任务顺序：

1. 建立 deterministic random 工具；
2. 生成地图边界、出生点、舰队和中立物；
3. 实现编队锚点、间距和朝向；
4. 实现多选、编组和队列指令；
5. 添加资源/状态栏、单位列表、快捷键提示和小地图占位；
6. 保存当前 seed，支持复制和重开。

验收标准：

- 相同 seed 生成相同初始遭遇；
- 不同 seed 能产生可玩而非空白或越界的遭遇；
- 多选单位能够发出一次共享指令；
- HUD 的数值和选中状态与 simulation 一致。

P4.1/P4.2/P4.3 的已验收范围：相同 URL seed 会生成相同的双方舰队规模和初始遭遇；不同 seed 会产生不同的可运行规模；中立小行星会进入场景并进行低速旋转；超出战场边界的移动指令会被限制；框选可选中多艘玩家舰船，`Control+1`/`1` 可绑定和召回控制组，`Shift+右键` 可追加移动队列；舰队列表、小地图、单位卡和遭遇状态与 simulation 同步；当前遭遇链接可复制，相同 seed 可重开，也可生成新 seed；战斗日志使用 simulation 时间并限制记录数量；小地图支持鼠标和键盘移动相机焦点并显示当前视野范围。deterministic encounter 与指令队列已有自动测试保护。

### P5：视觉表现

当前进度：已完成舰船视觉模块拆分、三舰种独立 builder、程序化舰体表面与粗糙度纹理、阵营贴花、生命值驱动损伤层、双层推进焰、命中闪光和高低特效降级路径。P5 保持 simulation 规则不变，并已通过固定 seed 的桌面、移动和实际战斗验收。

任务顺序：

1. 统一背景、灯光、雾和空间层次；
2. 为三类舰船建立可替换模型和材质接口；
3. 加入阵营色、边缘光、推进焰和武器挂点；
4. 加入武器轨迹、命中闪光、爆炸和受损反馈；
5. 加入选择框、目标线和战术标记；
6. 建立低画质/特效开关和降级路径。

验收标准：

- 远景能区分三类舰船和阵营；
- 近景没有明显材质、透明度或深度排序错误；
- 关闭特效后玩法和信息表达仍然成立；
- 固定视角截图能够支持前后版本视觉比较。

P5 已验收范围：远景可通过舰体轮廓和冷暖阵营色区分单位；近景可见舰体面板、粗糙度变化和识别贴花；受损舰船按生命值阈值显示损伤覆盖层；高特效提供外层推进焰、舰船点光源和命中闪光，低特效关闭这些高成本表现但保留推进核心、选中环、目标标记和武器轨迹。固定 seed `20260810` 的 1280×720 桌面、390×844 移动、选舰与实际交战检查均通过。

### P6：规模与性能

当前进度：第一版 P6 已完成。已加入 50/100/200 单位 deterministic 压力场景、可见/细节单位与 simulation/render/长帧/draw calls 仪表、10 Hz HUD 节流和舰队摘要缓存；远景舰船使用简化 LOD，并按阵营与舰种合并为最多 6 个实例批次；舰船点光源限制为 12，武器轨迹与命中/摧毁闪光使用 256 对象上限的复用池。实例批次保留 `instanceId -> unitId` 映射，远舰仍可点选并在选中后恢复完整细节。

任务顺序：

1. 建立单位数、可见数、simulation 时间、render 时间和长帧计数；
2. 用 50、100、200 单位建立压力场景；
3. 消除每帧无效分配和无界对象创建；
4. 引入对象池和可见性裁剪；
5. 对重复舰船和背景元素评估实例化；
6. 为远景加入 LOD 或简化渲染；
7. 记录不同浏览器/GPU 的压力结果。

验收标准：

- 压力场景不会出现明显输入失灵、逻辑停滞或内存持续增长；
- 每项优化都有 profiling 前后数据；
- 低性能设备有可理解的降级选项；
- 规模上限和已知瓶颈记录在进度日志中。

P6 已验收范围：固定 seed `20260810` 的 50/100/200 单位场景均保持确定性、唯一 ID 和战场边界；1280×720 内置 Chromium/WebGL 检查中，200 单位空闲场景从未优化高特效约 3,645 draw calls、179.97 ms render CPU 降至约 34 draw calls、2.35 ms render CPU；普通 4V3 遭遇仍保留完整材质、贴花、推进焰和点选反馈。200 单位远景点选、选中后完整 LOD、规模菜单、URL、重开/新 seed、390×844 布局以及池化效果的持续实际交战均已通过，控制台无异常。当前可选规模上限为 200；主 bundle 约 607.62 kB、跨浏览器/GPU 矩阵和更大地图的空间分批继续记录为 P7 限制。

### P7：验证与候选版

当前进度：`v0.1.0-rc.1` 候选版收口完成。simulation/deterministic 测试、HTTP smoke、固定 seed 桌面/移动视觉基线、普通遭遇核心交互、200 单位压力入口、已知问题和兼容性边界均已记录；独立 Firefox、Safari 和其他 GPU 验证暂缓，不作为当前候选版阻塞项。生产发布继续通过隔离 release 分支和人工 PR 完成。

任务顺序：

1. 补齐 simulation 单元测试和 deterministic seed 测试；
2. 建立启动、构建、核心交互 smoke test；
3. 为固定 seed 保存关键视角截图；
4. 修复阻断性 bug 和高优先级可读性问题；
5. 更新 README、进度日志和已知限制；
6. 通过 dev 推送后，按规范执行生产 release 分支和 PR。

验收标准：

- 新环境能按文档启动和构建；
- 核心路径没有已知阻断问题；
- 有至少一份固定 seed 的视觉回归记录；
- 有压力场景数据、浏览器兼容限制和发布说明；
- 生产发布通过 oc-prod-release 和人工 PR 检查。

P7 已验收范围：新环境可执行测试、类型检查和生产构建；线上 smoke 覆盖固定 seed、200 单位入口、关键 HUD 与实际 module script；固定截图覆盖 1280×720 普通/压力场景和 390×844 移动压力场景；Chromium/WebGL + Apple M3 Max 已验证选舰、暂停/恢复、高低特效与 200 单位实例拾取。主 bundle 约 608 kB、跨浏览器/GPU 矩阵、自动像素差异和超过 200 单位的首次加载内存继续作为候选版已知限制。

## 6. 推荐执行顺序

不要并行铺开所有系统，按以下最小依赖链推进：

~~~text
工程骨架
  -> 单舰 + 相机 + 选择
  -> 移动 + 暂停 + 重开
  -> 三类舰船 + 战斗
  -> 随机遭遇 + 编队 + HUD
  -> 视觉效果
  -> 性能优化
  -> 回归测试 + 发布候选
~~~

每个阶段都先做一条窄而完整的 vertical slice，再扩展数量和细节。遇到阻塞时优先降级资产复杂度、特效数量或地图规模，不跳过可测试的逻辑闭环。

## 7. 每次迭代的工作模板

每次开发更新应按以下顺序执行：

1. 在进度日志中写明 Scope 和验收目标；
2. 先实现最小可运行路径；
3. 添加对应逻辑测试或 smoke test；
4. 运行固定 seed 的视觉检查；
5. 记录性能、已知问题和未完成项；
6. 使用 oc-push 推送 dev；
7. 只有需要生产发布时才使用 oc-prod-release。

## 8. Definition of Done

一个任务只有同时满足以下条件才算完成：

- 功能在目标浏览器中可运行；
- 状态和边界情况已处理；
- 有相应测试、smoke check 或明确的人工验证记录；
- 没有把敏感信息写入代码、日志或文档；
- 文档和进度日志已更新；
- 工作区干净并已按开发流程推送；
- 如果影响生产，已通过 release 分支和 PR 流程。

## 9. 风险控制

### 规模风险

先用可控数量建立压力场景，不在没有 profiling 的情况下追求几千单位。达到瓶颈时按“减少无效更新、裁剪、对象池、实例化、LOD”的顺序优化。

### 视觉风险

先统一轮廓、颜色、空间层次和信息可读性，再增加高成本模型和后处理。每次视觉升级必须保留低画质降级路径。

### 范围风险

任何新功能先判断是否服务于“随机遭遇中的舰队控制”主循环。战役、联机、复杂经济和内容编辑器暂不进入第一版计划。

### 发布风险

dev 是日常开发源，prod 是经过隔离流程的发布仓库。禁止直接在 prod main 上修改文件；后续生产变化必须从 dev 拉取并使用 oc-prod-release。

### 预览环境风险

netcup1 的 `rts-game-dev.rococo.dev` 只用于 dev 构建验收。项目容器和共享 Nginx 配置分别由项目 Compose 与 `/opt/docker/rococo` 管理；每次变更必须先通过容器构建、Nginx 配置检查和浏览器 smoke test，再记录到日期进度日志。

## 10. v0.1.0-rc.1 之后的长期开发路线

P0 至 P7 已交付第一版随机遭遇 vertical slice 候选版，但不等于完整商业游戏完成。后续路线按“先提升可读性和可玩深度，再扩大内容和规模，最后做正式发布”的顺序推进。每个阶段都必须保持当前随机遭遇可运行，并通过独立的验收记录后才能进入下一阶段。

### P8：舰船资产与视觉质量升级

目标：把当前程序化原型视觉升级为具有统一美术规范、可替换资产管线和明确层级的舰队视觉，而不是只增加装饰数量。

当前进度：三舰种第一轮轮廓、第二轮程序化材质/贴花/分阶段损伤、第三轮 scout/striker/carrier glTF 2.0/PBR 正式资产试点，以及第四轮环境视觉基线均已通过固定 seed 的桌面/移动视觉评审。三舰种均具备资产清单、异步原子替换、显式程序化回退、网格/性能预算和 200 单位远景隔离验证；环境层级、材质、目标标记、战斗反馈和后处理预算已由 `src/render/environment-visuals.ts` 固化，selection、combat、LOD、实例化和高低特效路径保持稳定。P8 仅余声音设计接口未完成。

主要任务：

1. 固化 scout、striker、carrier 的轮廓、比例、功能识别和阵营变体设计稿；
2. 建立模型、材质、贴花、推进焰、武器挂点和损伤层的资源接口；
3. 逐步替换高频近景舰船为正式建模/PBR 资产，保留程序化 LOD 和实例化远景路径；
4. 增加小行星、背景层、目标标记和战斗反馈的统一材质与后处理规范；（已完成 P8 第四轮基线）
5. 补充音效、警报、攻击、命中、摧毁和 UI 反馈的声音设计接口；
6. 建立固定 seed 的桌面/移动视觉基线和人工评审清单。

验收标准：

- 三类舰船在远景、近景、低特效模式下都能区分；
- 资产替换不改变 simulation、选取、实例映射和 LOD 行为；
- 关键 UI、舰船材质和特效没有明显透明度、深度或移动端布局回退；
- 每个新资产都有来源、授权、尺寸、性能预算和回退方案记录；
- 至少完成一轮固定 seed 的视觉评审，并在进度日志中记录未通过项。

### P9：战术玩法与敌方 AI 深化

目标：让随机遭遇从“能控制和交战”提升为具有明确决策、反制和重玩价值的 RTS 对局。

主要任务：

1. 把移动、攻击、停止、护航、集火和撤退整理为一致的指令语义；
2. 增加侦察范围、视野/目标发现、威胁评估和目标优先级；
3. 为敌方舰队加入分层 AI：巡逻、接敌、编队、集火、撤退和重组；
4. 增加舰船角色之间的克制关系、冷却窗口和资源化的战术取舍；
5. 补充胜负条件、战斗后统计、重播所需的 deterministic event 记录；
6. 为 AI 和指令系统增加纯 simulation 测试，避免依赖 Three.js 场景才能验证。

验收标准：

- 固定 seed 与固定输入可以重现相同的关键战斗事件；
- AI 不会出现无目标死循环、越界、无限生成或不可恢复的停滞；
- 玩家能理解单位当前目标、威胁和指令状态；
- 至少三种 AI 行为在普通遭遇中可观察，且高低特效不影响规则结果；
- P9 的新增规则有自动测试和至少一份线上浏览器实战记录。

### P10：遭遇内容与单局结构

目标：在保持随机模式为主的前提下，提供多种可控、可复现且有明确节奏的遭遇，而不是只扩大单位数量。

主要任务：

1. 把遭遇生成拆为地图、阵营、目标、环境危险和胜负条件等可组合模块；
2. 增加资源点、护送、搜索、歼灭、防守或限时目标中的最小可玩子集；
3. 增加遭遇难度、地图规模和舰队配置的可配置 schema；
4. 加入遭遇选择、结果页和 seed/配置分享格式；
5. 建立异常 seed、不可解遭遇、越界和软锁检测；
6. 评估是否需要轻量战役/任务入口，但不在没有内容数据前先实现复杂编辑器。

验收标准：

- 至少三种遭遇目标可以通过固定 seed 复现并自然结束；
- 生成器不会产出空场、无目标、必败或无法完成的默认遭遇；
- 遭遇配置与 simulation 解耦，能被测试和版本化；
- HUD 能清晰表达当前目标、进度、失败和胜利原因；
- 新内容不会破坏现有默认随机遭遇和 URL 分享。

### P11：规模、兼容性与可观测性

目标：在真实设备和真实加载数据支持下，决定是否把规模上限从 200 提高，并完成正式支持范围定义。

主要任务：

1. 建立独立 Chrome、Firefox、Safari 及 Windows/NVIDIA/AMD/Intel 和不同 Apple GPU 的验证矩阵；
2. 接入可重复的截图像素差异、长时间交战、内存和资源释放采样；
3. 将每个单位的完整近景视觉改为按距离和可见性延迟创建、共享或销毁；
4. 将远景实例批次从整图扩展为空间分块，并恢复合理的批次级裁剪；
5. 根据真实加载瀑布决定 vendor 分包、压缩、缓存和资源预加载策略；
6. 明确最低支持浏览器、设备档位、默认特效和压力场景上限。

验收标准：

- 每个声明支持的浏览器/设备都有可追溯验证记录；
- 自动视觉回归有稳定阈值、基线更新规则和失败产物；
- 长时间 200 单位交战没有持续增长的 simulation、DOM 或 GPU 资源；
- 若提高规模上限，必须有 profiling 数据、降级方案和回退上限；
- 性能结论区分 simulation CPU、renderer 提交 CPU、GPU、内存和网络加载指标。

### P12：正式版发布与运营基础

目标：把经过验证的版本从候选版推进为可维护、可回退、可发布的正式版本。

主要任务：

1. 完成 P8 至 P11 的阻塞项审计，建立正式版 scope freeze；
2. 完善版本号、变更日志、回滚说明、运行手册和故障排查文档；
3. 增加生产构建的健康检查、静态资源缓存核验和部署后 smoke test；
4. 明确 dev、release bridge、prod 和预览域名的职责边界；
5. 为关键错误、加载失败和性能回退建立最小日志/监控方案，但不记录敏感数据；
6. 通过独立 release 分支、PR、人工审核和部署验证发布正式版本。

验收标准：

- 新环境可按文档构建、启动、验证和回滚；
- 正式版本有明确支持范围、已知问题和升级说明；
- 生产发布可验证、可回退，且不会依赖开发预览容器；
- 进度日志、发布说明和仓库标签对应同一个版本提交；
- 未完成的功能明确留在下一版本计划，不以“暂时能运行”冒充完成。

### 长期路线的优先级与停止条件

- P8 优先处理当前最明显的资产质量问题；如果视觉资产尚未达到可评审标准，不提前扩大 P10 内容范围。
- P9 优先保护 simulation 可测试性；任何 AI 或战术规则都不得只写在渲染层。
- P10 先做少量可复现遭遇，再决定是否投入战役和编辑器。
- P11 只有在有真实设备数据时才提高 200 单位上限；没有数据时保持当前上限。
- P12 只有在支持范围、回退流程和已知问题都明确后才称为正式版。
