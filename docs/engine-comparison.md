# 渲染与游戏框架对比

## 1. 结论先行

本项目不是“只能用 Three.js”，但如果目标是家园风格的 3D 宇宙 RTS，Three.js 是最合适的核心基础。

推荐组合：

> Three.js（3D 战场与舰队渲染） + DOM/CSS/Canvas（HUD 与菜单） + 可选的 PixiJS 局部 2D 模块。

Phaser 3 和 Phaser 4 都可以做出优秀的 2D RTS 或 2D 原型，但不建议作为本项目 3D 舰队战场的主引擎。PixiJS 适合高性能 2D 渲染，但单独承担 3D 战场会需要自行补齐相机、空间变换、模型、材质、灯光、碰撞和 3D 资产管线。

## 2. 选型标准

重点比较：

- 3D 场景、透视相机和舰队空间关系；
- 着色器、材质、后处理、粒子和实例化；
- 大量单位的批量渲染、LOD 和对象生命周期管理；
- 选择框、HUD、小地图、输入、相机和游戏循环；
- 资产生态、团队学习成本、可调试性和长期扩展性。

## 3. 对比表

| 方案 | 定位 | 3D 战场适配 | 2D UI/HUD | 舰队渲染/着色器 | 主要代价 | 本项目建议 |
| --- | --- | --- | --- | --- | --- | --- |
| **Three.js** | 3D Web 渲染库 | 最强，场景图、相机、几何、材质、灯光和动画都围绕 3D | 需要自行选 DOM/CSS、Canvas 或其他 UI 方案 | 直接控制材质、Shader、实例化、批处理和后处理 | 不是完整 RTS 引擎，选择、寻路、战斗、存档需自建 | **核心方案** |
| **PixiJS** | 2D Web 渲染库 | 不以原生 3D 舰队为目标；可做 2D 假 3D 或承担局部 2D 层 | 很适合小地图、图标、特效和大量 2D 精灵 | 2D 批处理强；完整 3D 管线需额外搭建 | 与 Three.js 同时使用会增加坐标、输入和生命周期同步成本 | **可选局部模块** |
| **Phaser 3** | 2D 游戏框架 | 适合 2D RTS；不适合作为高质量 3D 舰队核心 | 内置场景、输入、动画和常用游戏能力，2D 迭代快 | 主要服务 2D 场景；3D 舰船需外接方案 | 3D 需求会绕开框架主路径，最终形成两套系统 | 2D 原型可用，核心不选 |
| **Phaser 4** | 新一代 2D 游戏框架/渲染架构 | 仍应按 2D-first 方案评估，不能把更新的渲染器等同于完整 3D 引擎 | 适合 2D UI、场景和交互原型 | 需要核对目标版本的渲染能力与稳定性；不应假设具备 Three.js 级 3D 工作流 | 版本/生态成熟度与 3D 资产管线仍需单独验证 | 2D 项目可评估，核心不选 |

## 4. 逐项分析

### 4.1 Three.js

Three.js 的优势是把最重要的困难暴露给项目本身：3D 场景、相机、坐标系、几何、材质、灯光、动画、粒子和 GPU 资源都可直接控制。这正适合需要“舰船细节 + 巨大尺度 + 自定义视觉效果”的项目。

它不是现成的 RTS 框架，因此必须自行设计：

- 单位数据模型与状态机；
- 选择、编队、队列、攻击和战斗计算；
- 空间索引、碰撞/避障、寻路和对象复用；
- HUD 状态同步、输入映射和存档；
- 性能预算、LOD、实例化和可视性裁剪。

这项工作量较大，但不会被 2D 引擎的抽象限制住。对于本项目，控制权比“开箱即用的 2D 游戏循环”更重要。

### 4.2 PixiJS

PixiJS 很适合做 2D 渲染密集的界面和小地图：图标、标记、指令队列、粒子和大量精灵都可以得到较好的批处理性能。它也可以用于 2D 俯视 RTS，但如果主战场需要真实透视、自由旋转相机、模型材质和空间光照，就会重复实现许多 Three.js 已经提供的能力。

因此，第一版不把 PixiJS 和 Three.js 同时作为必需依赖。先用 DOM/CSS/Canvas 做 HUD，等小地图或标记层成为瓶颈，再以边界清楚的 2D overlay 引入 PixiJS。

### 4.3 Phaser 3

Phaser 3 的强项是快速构建 2D 游戏：场景、输入、精灵、动画、相机和常用游戏循环都很成熟。它适合验证“随机遭遇 + 选择单位 + 指令 + HUD”的 2D 玩法，但不适合承载本项目的核心 3D 视觉目标。

如果先做 2D vertical slice，Phaser 3 是合理选择；如果最终必须迁移到 3D 舰队，迁移成本可能高于直接用 Three.js 做一个低保真 3D slice。

### 4.4 Phaser 4

Phaser 4 应按其目标版本的官方文档和发布状态进行验证。即使渲染器和底层能力有所更新，它仍然应被视为 2D-first 的游戏框架，而不是与 Three.js 对等的 3D 场景/资产工作流。

它可作为 2D 原型或独立 2D RTS 的候选，但不应因为“新版本”就假设它会自动解决 3D 舰船模型、材质、灯光、自由镜头、空间编队和大规模 3D 实例化问题。

## 5. 推荐架构

~~~text
游戏逻辑层
  ├─ 单位/编队/战斗/随机遭遇
  ├─ 选择/输入/指令队列
  └─ 性能统计与回放数据

Three.js 战场层
  ├─ 场景、相机、星空和空间坐标
  ├─ 舰船模型、材质、Shader、粒子和后处理
  ├─ 实例化、LOD、可视性裁剪和对象池
  └─ 射线拾取、屏幕坐标与世界坐标转换

界面层
  ├─ DOM/CSS：菜单、面板、文字和可访问交互
  ├─ Canvas：简单标记、连线或调试 overlay
  └─ 可选 PixiJS：高密度 2D 小地图/图标层
~~~

## 6. 最终决策

1. **核心引擎：Three.js。** 先以 WebGL 可运行作为基线，再评估 WebGPU/现代着色器路径。
2. **UI：先 DOM/CSS + Canvas。** 避免为了 HUD 过早引入第二套渲染器。
3. **PixiJS：保留为可选依赖。** 只有当 2D overlay 的数量或批处理需求证明它有价值时再引入。
4. **Phaser 3/4：不用于主战场。** 它们适合 2D 玩法实验，不改变本项目的 3D 主路线。
5. **版本锁定：** 初始化工程时读取各官方包的当前稳定版本，并用锁文件固定；不要在文档中预先写死未经验证的版本号。
